## 3. User and Authentication Model

Supabase Auth is the source of authenticated users.

`profiles.id` references `auth.users.id`.

User roles:

- `user`
- `admin`

User status:

- `active`
- `suspended`

A database trigger synchronizes newly created Supabase Auth users into `public.profiles`.

Function:

`public.handle_new_user()`

Trigger:

`on_auth_user_created`

The profile synchronization uses:

- Auth user ID
- email
- nickname from metadata when available
- email username as fallback nickname
- avatar metadata when available
- email confirmation status

## 5. Activity Model

Activities are stored in `activities`.

Important fields include:

- `id`
- `host_id`
- `title`
- `category_id`
- `cover`
- `starts_at`
- `ends_at`
- `location`
- `district`
- `participant_limit`
- `fee`
- `deposit`
- `agenda`
- `eligibility`
- `description`
- `status`
- `is_private`
- `room_password`
- `invite_token`
- `created_at`
- `updated_at`

The activity host is referenced by:

`activities.host_id → profiles.id`

The category is referenced by:

`activities.category_id → activity_categories.id`

The actual activity time is stored using:

- `starts_at`
- `ends_at`

`time_ranges` is used as configurable/filter data and is not the source of the actual activity time.

## 6. Activity Status State Machine

The verified activity states are:

- `published`
- `confirmed`
- `cancelled`
- `completed`

Business meaning:

### published

Activity is live and collecting participants.

Chat is closed.

### confirmed

Creator confirms that the activity will proceed.

Chat opens.

### cancelled

Activity will not proceed.

Chat closes.

### completed

Activity has finished.

Chat remains available according to the configured post-event period.

Allowed transitions:

```text
published → confirmed
published → cancelled
confirmed → cancelled
confirmed → completed
